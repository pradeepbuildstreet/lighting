# Resolution history and audited reversal UI

/admin/catalogue/resolutions retains original group outcomes, snapshots and linked audit/review evidence as read-only. A separate explicit reversal panel inspects the current revision, latest audit/review identity, target and incoming links. It requires a reason, acknowledgement and exact-request confirmation. The backend revalidates all expectations atomically. No migration is applied by this source change.

The request is saved to session storage before sending. Timeout, failed receipt verification and reload preserve the identical request/key. A verified receipt must match the selected product, originating resolution, reason, revisions and inactive/unpublished unapproved draft outcome. Invalid recovery data blocks new submissions until explicitly cleared; clearing does not undo a server event. Busy/dirty states protect link navigation and unload and lock main workspace scope. Browser history/back and all rendered interaction paths still require browser verification.

Product and group reversal history uses authorized, repeatable-read 50-event keyset pages. Product history includes events affecting that product as a former primary. Group events are attached to the original group identity without changing its original records. Missing database prerequisites are displayed as unavailable, not as an empty verified history. Bigint revision fields are serialized as text where JSON number decoding could lose precision.

Preparation verification: seven isolated executable request/recovery/receipt helper cases and eight mocked/source inspection/history service cases passed in an offline Node harness. These are not a full repository run, frontend type-check/build, PostgreSQL functional tests, browser tests, or deployment verification. All those gates remain pending. The verification JSON reports are preparation artifacts, not production receipts.
