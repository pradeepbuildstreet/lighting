# Server-side version-3 import jobs

Backend implementation only. The existing version-3 UI still validates only: manifest hashing, job preparation, sequential staging, uncertain-outcome recovery and commit buttons must be wired next. No migration is applied by this commit. Tag-policy masters, editable naming rules and remaining general-editor changes are still pending.

Apply migration 08 only after isolated integration tests and separate approval. Migration 07 and nullable-client compatibility are required before enabling product writes. New commit requests default disabled; explicit CATALOGUE_IMPORT_V3_COMMIT_ENABLED=true and installed identity/job migrations are required. This flag is NOT evidence of successful rollout verification. Existing committed results remain recoverable when writes are disabled.

Endpoints under /api/admin/catalogue/taxonomy/imports-v2/v3/jobs: GET /state; POST / with XLSX file, request_key UUID, local_root and JSON manifest; GET /request/:key; GET /:id; POST /:id/files with file, relative_path and preview_token; POST /:id/commit with preview_token and explicit confirm_updates boolean; DELETE /:id with preview_token for discard/expired cleanup. Keep the request key before sending a preview request. On uncertain preview outcome recover by that key; on uncertain commit recover the same job. Do not create replacement jobs to resolve unknown outcomes.

The server persists an immutable token-bound preview and image manifest (path, SHA-256, byte length). Quotas: 100 product rows/job, 200 images/job, 25 MiB/image, 250 MiB/job, five active previews and 500 MiB active manifest bytes per owner. Previews expire after two hours; committed result receipts do not expire. Same-owner input digest replay returns the existing live preview or committed receipt, including across different request keys. Deliberate identical reimports require a separately designed override; none is supplied.

Image inspection verifies signatures/basic framing for PNG/JPEG/WebP and SHA-256/size against the manifest. It is NOT a full image decoder, CRC validator, malware scanner or decompression-bomb defense for every codec; strengthen decoder-level verification before considering this production-hardened. Staging ignores browser MIME/extension claims and uses detected MIME/server-generated keys. Files are private, written exclusively and fsynced. Commit rereads and hashes them. Missing or modified files fail closed.

Product/content/media writes, final revisions, audit events and the committed receipt use the same database transaction. Commit checks current reference fingerprint and saved product revisions. New products stay unnamed/SKU-pending and unpublished; no SKU/name generation, review approval or publication occurs during import. Existing primary images are retained; otherwise the first supplied image becomes primary. Image order follows workbook order, appended after existing images. Per-product matching SHA-256 associations are reused rather than duplicated.

Filesystem and PostgreSQL are not a distributed transaction. Deterministic job/path/digest-derived filenames make files left before a failed staging-ledger commit discoverable from the persisted manifest. Cancellation/expired-job cleanup derives all possible image suffixes, holds the job lock and refuses to unlink any product-referenced key. Committed jobs cannot be cancelled. Failed cleanup is safe to retry. Automatic scheduled cleanup, disk-space monitoring, durable/shared media-volume verification and operator tooling are not implemented here.

Twelve core manifest/signature/authorization helper cases passed locally. Required before activation: actual PostgreSQL migration tests and role grants, parallel/retried preview/stage/commit tests, rollback after partial row/media writes, fault-injected storage/DB-commit failures, cancelled/expired cleanup races, content-duplicate behavior, JPEG/WebP fixture coverage, HTTP/admin authorization tests, full backend/frontend suites, type-check, production build and browser UAT. Current DB statement/lock timeouts and shared media-volume semantics must be load-tested. No production-ready claim is made by this backend increment.
