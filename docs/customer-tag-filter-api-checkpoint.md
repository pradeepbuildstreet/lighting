# Customer tag-filter API checkpoint

Base: release d149c3521069ec17e1e663f264210f52e2056e15. Adds GET /tag-filters under the existing public catalogue API. Existing GET /products delegates to tag-aware SQL only when tag_filters is supplied; ordinary requests retain the legacy listing path. Existing read-only/public-enabled/readiness/rate-limit/security headers remain. No admin endpoint or write operation is added.

Selection format: JSON array of {group_id,tag_ids,unclassified}. Canonical UUID validation, duplicate-group rejection and operational bounds apply (20 selected groups, 100 tags/group, 200 tags total, 16000 JSON characters). OR within a group, including Not classified; AND across groups. Configured global groups control all-products listing visibility. Active direct-category local assignments determine branch-specific per-product applicability. Category listings derive group unions from eligible descendants without editable parent inheritance. Informational tags outside applicable groups do not become filter matches or Not classified.

Products, total, primary media and categories are read in one repeatable-read read-only transaction using public_products and active primary ancestry. Public DTO construction reuses the existing mapper. Tag counts apply other groups but exclude the counted group's own selection; distinct products prevent double counting. All-unclassified groups are hidden; selected labels are returned separately. Choices load per group with prefix search and pagination (50 default/100 maximum), retaining selected zero-count active tags. No tag named Not classified is stored. Scopes above 200 configured groups fail rather than silently truncate. Five-second statement timeouts are operational guards, not measured performance.

Validation: 22 isolated parser/mocked-facet/SQL-structure tests and JavaScript syntax checking passed in preparation. An approved combined literal EXPLAIN plus availability batch completed on live PostgreSQL without SQL error. The connector returned only the availability summary, not the detailed plan. This is not EXPLAIN ANALYZE, realistic selectivity/performance testing, semantic tests over seeded tag combinations, complete service-role/HTTP or concurrent execution acceptance. Full repository suite/CI remains unverified.

Live availability at validation: taxonomy versions 1 and 2; one published product, zero published tagged products, four category-group assignments, zero global group assignments. Empty customer tag choices are expected until applicable groups and published classified data exist. No assignments, tagging, approval, publication, SQL prerequisites or activation markers are automatically changed.

This commit publishes backend capability only. Customer controls, URL propagation/chips and product-first lazy-facet UI integration are the next checkpoint. It does not claim customer tag filters are fully usable yet. Existing brand/currency facets, product-kind restriction, compatibility, wishlist, media writes and main are unchanged.
